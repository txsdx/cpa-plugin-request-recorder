# v0.8.2 性能基准

对比基线为 v0.8.1（`561ddbfc19d00052cb558775178e1858595d088a`）。将同一份 [performance_test.go](../internal/recorder/performance_test.go) 放入两个 checkout，在同一 Linux amd64 环境依次执行；Go 1.26.10，Intel Xeon Platinum 8573C，Go 自动选择 `GOMAXPROCS=5`。每项运行三次，以下取中位数。性能测试未开启 race，正确性回归另外开启 race。

```bash
go test -tags=nodynamic ./internal/recorder -run '^$' \
  -bench 'Benchmark(CatalogRefresh|CatalogUncached|RecordRead|ConversationSave)$' \
  -benchmem -benchtime=500ms -count=3
```

| 合成场景 | v0.8.1 耗时 | v0.8.2 耗时 | v0.8.1 分配 / 次 | v0.8.2 分配 / 次 |
| --- | ---: | ---: | ---: | ---: |
| 1 万条记录，首屏 50 条，未缓存读取 | 272 ms | 2.17 ms | 45.31 MiB | 236 KiB |
| 同上，忽略已拒绝条目，未缓存读取 | 273 ms | 1.58 ms | 43.85 MiB | 251 KiB |
| 1 万条记录，同一页未变化，管理列表响应 | 270 ms | 0.064 ms | 45.80 MiB | 106 KiB |
| 约 2 MiB 会话，打开回放 | 104 ms | 63.9 ms | 55.04 MiB | 25.95 MiB |
| 同一会话，读取完整原文响应 | 132 ms | 100 ms | 87.74 MiB | 60.66 MiB |
| 约 3 MiB 历史，从明确响应边界重生成并保存 | 181 ms | 156 ms | 131.01 MiB | 73.45 MiB |

分配量是 Go benchmark 的累计 `B/op`，会被垃圾回收；它不是常驻 RSS、峰值存活对象或网络传输大小。耗时包含测试环境的调度、GC，以及保存场景的数据库写入；不能换算成用户服务器固定的 CPU 百分比。不同轮次有波动，尤其是大正文的 JSON 编码与写入。所有内容都是合成文字，不包含真实请求或密钥。

默认列表的未缓存读取基准直接调用 `Store.List`，因此不依赖响应缓存，代表新记录不断使缓存失效时的读取路径。计数在事务内维护，首屏只读取足够的摘要。未变化页基准调用管理 API 生成列表响应；缓存只保留最近一页，最多 1 MiB，返回时复制字节。复杂筛选或全文搜索在数据变化后仍需扫描摘要，未变化时可复用同一页结果。深分页仍需越过前面的条目，不能把首屏结果推广到任意 offset。

长会话基准包含约 1 MiB 用户文本与约 1 MiB 模型文本。回放只加载会话正文；完整原文读取继续返回完整请求和响应。保存基准用已记录的 `previous_response_id` 重生成后续回答，计时前预热到固定约 3 MiB 历史，并逐次确认历史长度不增长，避免不同 `b.N` 混入不同长度的会话。

主要修改：

- 总数与拒绝数随记录事务更新，状态诊断和首屏列表不再为计数遍历全库。
- 同一快照的摘要、计数、版本一起读取。新请求、用量和别名更新、保留清理立即失效；图片状态和设置写入不使摘要缓存失效。
- gzip 解压器复用，清除交易 mmap 引用后才归还池；按已知长度分配缓冲区，继续验证 SHA-256、长度与 gzip CRC / 完整 trailer。
- 回放和图片归档只读取会话正文；原请求和响应按需读取，完整导出继续保留原文和原图。
- 单次会话匹配复用已解压的记录；已有明确会话命中时，不额外计算用于无 ID 匹配的上下文索引。

现有 conversation-v1 数据库首次打开时，仅从摘要生成一次计数索引，无需删除或重建正文。计数与版本随在线数据库整理一起复制和重放；事务回滚也回滚计数。

这些优化没有限制对话文字、可见思考、工具和原图的保存内容，也没有延长默认 1 秒的列表刷新间隔。首次大图解码 / WebP 编码仍是开销较大的工作，一次预览转换、32 MiB 压缩预览缓存和图片下载并发限制继续生效。`max_memory_bytes` 管的是进行中的采集正文预算，JSON / 解压临时对象、Go 运行时、数据库映射和图片解码内存不包含在该预算中。
